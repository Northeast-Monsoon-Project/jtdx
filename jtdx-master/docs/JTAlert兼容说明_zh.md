# JTDX-F V3.6.6 与 JTAlert

本轮针对用户报告的 **JTAlert 2.81.7 无法连接 JTDX-F、原版 JTDX 2.2.159 可以连接**，修正程序发现、窗口标题、配置查找与 UDP 身份之间的不一致。JTDX-F 仍是独立分支，使用自己的设置和日志。

## 已确认的问题与证据范围

V3.6.5 的主程序名为 `jtdx-f.exe`，应用名称为 `JTDX-F`，窗口标题在版本之前插入了 `by Fluxmancer`，配置使用独立的 `JTDX-F.ini`。这些都是可以从本项目源码确认的差异。

另一个 JTDX 分支的作者记录了实际 JTAlert 诊断：JTAlert 查找 `jtdx.exe` 进程，并从窗口标题中解析电台实例名，再寻找对应的 `JTDX - 实例名.ini`，从中取得 UDP 地址和端口。署名出现在版本号之前，会被误识别为实例名，导致查找错误的配置文件。作者通过将署名移到版本号之后修复了发现问题。详见其 [修复提交与诊断注释](https://github.com/ce3tsk/jtdx_contest/commit/635aba449b0d36b6685086c2874b8efbccd85289)。

这提供了明确的兼容性修复依据，但不等于已经在用户的 JTAlert 2.81.7 上复现全部失败过程。尚未取得用户现场的 JTAlert 诊断，也未确认该版本对 UDP 实例 ID 的全部匹配规则。因此，不能把故障简单归因于“V3 版本号不受支持”或“UDP 协议已经不兼容”。

## 本版的兼容方式

| 项目 | V3.6.6 行为 |
| --- | --- |
| 产品、安装目录和主配置 | 继续使用独立的 JTDX-F |
| Windows 实际主程序 | JTDX-F 安装目录中的 `jtdx.exe` |
| 原来的启动路径 | `jtdx-f.exe` 保留为启动器，转交给同目录主程序 |
| 默认 UDP 实例身份 | `JTDX - JTDX-F`，与原版 `JTDX` 区分 |
| 窗口标题 | 兼容实例名之后立即放实际版本 `v3.6.6`，团队署名移到版本之后 |
| JTAlert 发现配置 | `%LOCALAPPDATA%\JTDX - JTDX-F\JTDX - JTDX-F.ini` |

发现配置仅投影所需的 UDP 配置、当前呼号和网格，并附带文件归属标记；它不是另一套工作配置，不存放通联日志、CAT/PTT、音频或 MCP 令牌。软件仍从原来的 JTDX-F 配置读取设置，保存设置和切换呼号后更新投影，不把投影内容读回。若目标文件不属于本分支，程序不覆盖它。

使用 `--rig-name=FT450` 启动独立实例时，应用名仍为 `JTDX-F - FT450`，对应窗口、UDP 与发现配置名为 `JTDX - JTDX-F - FT450`。其发现文件位于 `%LOCALAPPDATA%\JTDX - JTDX-F - FT450\JTDX - JTDX-F - FT450.ini`；主配置位置继续沿用该 JTDX-F 实例自己的目录。

本轮也修正了 UDP 回复定位解码行时的时间格式：FT4 的 `+` 标记此前可能按四位 `HHMM` 重建消息，而界面使用六位 `HHMMSS`，导致收到回复请求却找不到原解码。现在 FT 系列模式及使用秒时间的上游模式采用六位时间，旧分钟制模式保持原格式。这项修正包含本分支 FT2 回复路径，但不表示 JTAlert 已支持 FT2。

## 连接步骤

1. 安装 V3.6.6，先启动 JTDX-F，在“设置 → 报告”确认主 UDP 服务器地址和端口。全新配置默认 `127.0.0.1:2237`；升级会保留已有设置。
2. 同机使用时，保持 JTDX-F 与 JTAlert 的 UDP 地址、端口一致。不要把用于 ADIF 广播的第二 UDP 端口当作主消息接口。
3. 若要在 JTAlert 中点击呼号并请求回复，在 JTDX-F 勾选“接受 UDP 请求”，并检查“接受 UDP 回复消息”的类型筛选。仅显示解码和状态不要求此开关；开启它也不会授权发射。
4. 启动 **JTAlert for JTDX**，检查其识别到的运行实例。先启动 JTDX-F，可让发现配置在 JTAlert 检测前就绪。
5. 修改 UDP 地址或端口后，保存 JTDX-F 设置并重启 JTAlert，使其重新读取发现信息。

若同时运行原版 JTDX 和 JTDX-F，应为各自连接分配不同端口，并在 JTAlert 中确认对应实例；不要仅凭两个程序均显示 `jtdx.exe` 来判断接错。它们安装在不同目录，工作配置和日志也分别保存。第三方自动启动工具可继续使用原来的 JTDX-F `jtdx-f.exe` 完整路径。

## 降级到 V3.6.5 及更早版本

V3.6.6 在 Windows 安装目录新增实际主程序 `bin\jtdx.exe`，原 `bin\jtdx-f.exe` 保留为启动器。已发行的 V3.6.5 及更早安装器只覆盖其已知文件，直接安装旧包不会删除新增的 `jtdx.exe`；如果 JTAlert 自动启动仍指向它，就可能启动残留的新版程序。

需要退回这些旧版本时，建议先卸载 V3.6.6，再安装旧包，并把第三方启动路径改回旧版 `jtdx-f.exe`。卸载保留独立用户数据目录中的日志和设置；不要手动删除该目录。本轮没有验证旧安装包直接覆盖能完成全部文件的降级。

## 发射授权和排查

JTDX-F 仍要求人工开启发射会话。处于停止状态时，即使 JTAlert 能显示解码、点击呼号并发来回复请求，也不能重新授权发射；应在 JTDX-F 人工点击“启用发射”。已有授权的会话继续遵守永久黑名单、监管、消息筛选及收发状态限制。第三方点击与本机人工双击启用发射是不同操作。

无法连接时，先区分“未发现程序”“发现但没有解码”和“有解码但不能回复”：分别核对启动顺序与实例标题、主 UDP 地址和端口、接受请求及发射授权。若发现配置位置已有其他程序创建的同名文件，不要直接删除或覆盖；保留文件后核对来源。仍失败时，保留 JTAlert 版本、诊断中的窗口标题与 INI 路径、UDP 设置及复现步骤，供继续定位。

## 验证边界与资料

本版的本地协议和界面回归属于 JTDX-F 端的离线验证。获取官方安装包时，下载服务器返回 HTTP 403，**未实际运行 JTAlert 2.81.7，不能宣称已经完成该版本的真实连接验收**。最终通过项目及安装包校验值以随版验证记录为准；这些验证不涉及实体电台射频发射。

- [JTAlert 官方下载与依赖说明](https://hamapps.com/JTAlert/)：安装要求、运行库和官方分发入口。
- [JTAlert 官方版本记录](https://hamapps.com/php/notes.php?file=jtalert)：2.81.7 是用户现场版本，后续版本的行为不能直接当作 2.81.7 已验证的行为。
- [JTDX Contest 作者的修复提交](https://github.com/ce3tsk/jtdx_contest/commit/635aba449b0d36b6685086c2874b8efbccd85289)：进程、窗口标题与 INI 查找关系的一手诊断依据。
- [上游 JTDX 报告设置说明](https://github.com/jtdx-project/jtdx/blob/master/doc/user_guide/en/settings-reporting.adoc)：UDP 地址、端口及合作程序接口。
